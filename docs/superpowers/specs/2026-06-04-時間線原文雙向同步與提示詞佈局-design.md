# 時間線原文雙向同步與提示詞佈局改造

- **狀態**：Draft
- **日期**：2026-06-04
- **範圍**：`frontend/src/components/canvas/timeline/`、後端 Step 1 草稿同步服務

---

## 1. 背景與問題

劇集工作區的時間線有三個 tab：**預處理**、**分鏡時間線**、**影片時間線**。其中：

- **預處理 tab**（`PreprocessingView`）編輯的是 **Step 1 草稿**（`drafts/episode_N/step1_*.md`，Markdown 表格，逐片段一列）。
- **分鏡 / 影片 tab** 的 `SegmentCard` 第一欄編輯的是**切片後的 segment 內容**（narration 的 `novel_text` / drama 的 `scene_description`），存於 script 檔。

兩者是同一批原文在「切片前 / 切片後」的兩種型態。生成劇本後，兩份資料各走各的：改 segment 不回寫草稿，改草稿不重切 segment。使用者直覺認為「預處理跟原文應該一致，否則白存」。

此外，`SegmentCard` 的 Image / Video Prompt 區塊把「選模型 + AI 產生」擠在標題列右側，導致下拉被壓到 `w-32`、按鈕 `text-[10px]`，空間不足、字太小。

### 兩種模式的差異（釐清用）

| | narration（說書） | drama（戲劇） |
|---|---|---|
| 草稿檔 | `step1_segments.md` | `step1_normalized_script.md` |
| 片段稱呼 | 片段（`G01`…） | 場景（`E1S01`…） |
| segment 內容欄 | `novel_text` | `scene_description` |
| SegmentCard 第一欄現況 | 「原文」可編輯 textarea | 「對話」唯讀列表（**無可編輯原文框**） |

兩種草稿都是 Markdown 表格，結構一致：**第 1 欄 = 片段 ID，第 2 欄 = 內容，後續為衍生欄（字數 / 時長 / segment_break）**。`get_source_paragraphs`（`server/routers/project_episodes.py:751`）已用同一段 parser 解析兩模式。

---

## 2. 目標

1. **提示詞佈局改造**：Image / Video Prompt 兩塊的「選模型 + AI 產生」從標題列右側移到 textarea 下方一整列；下拉變寬、字放大。
2. **原文雙向同步**：segment 內容欄 ↔ Step 1 草稿表格，**雙向**即時同步，**narration 與 drama 都做**。同步「內容欄」並自動重算字數；時長 / segment_break 等其餘欄位保留原值。
3. **前端兩模式一致**：drama 的 `SegmentCard` 第一欄補上可編輯的「場景描述」框，與 narration 的原文框統一，雙向同步入口齊全。
4. **邏輯抽共用**：同步邏輯集中在後端單一模組，narration / drama 用同一套程式以參數區分，不重複寫。

### 非目標

- 不做「整段重切」：草稿已是逐列表格，靠片段 ID 對齊，不重跑切分演算法。
- 不改動 segment 邊界、提示詞、已生成媒體。
- 不在草稿同步時保留 Markdown 標題 / 額外格式（草稿本就是純表格）。

---

## 3. 架構

### 3.1 後端共用同步服務（方案 A）

新建 `lib/step1_draft_sync.py`，集中所有「草稿表格 ↔ script」邏輯。模式差異收斂到一張設定表：

```python
@dataclass(frozen=True)
class DraftMode:
    filename: str            # step1_segments.md / step1_normalized_script.md
    id_header_aliases: set   # {"片段", "片段 ID", ...} / {"場景 ID", "場景ID", ...}
    segment_field: str       # "novel_text" / "scene_description"
    script_items_key: str    # "segments" / "scenes"
    item_id_key: str         # "segment_id" / "scene_id"

DRAFT_MODES = {"narration": DraftMode(...), "drama": DraftMode(...)}
```

提供的函式（皆 mode-agnostic，吃 `DraftMode`）：

- `parse_draft_table(md) -> list[DraftRow]`
  抽出 `get_source_paragraphs` 的 parser，回傳結構化列（`{id, content, raw_cells}`）。`get_source_paragraphs` 改為複用此函式。
- `render_draft_table(rows, mode) -> str`
  反向渲染回 Markdown 表格，**內容欄重算字數欄**（`len(content)`），其餘欄沿用 `raw_cells`。
- `sync_segment_to_draft(project, episode, segment_id, new_content, mode)`
  改 segment → 讀草稿 → 找到對應 ID 列 → 換內容 + 重算字數 → 寫回草稿檔。
- `sync_draft_to_segments(project, episode, new_md, mode) -> int`
  改草稿 → 解析新表格 → 依片段 ID 對齊回寫各 segment 的內容欄到 script。回傳更新數。
  - **ID 對齊**：以草稿列的片段 ID 為準，逐列 match script 中同 ID 的 segment；找不到對應 ID 的列略過（不新增/刪除 segment），記 log。

### 3.2 同步的觸發點（後端擴散，前端只打單一 API）

| 使用者動作 | 既有寫入路徑 | 新增擴散 |
|---|---|---|
| 在 SegmentCard 改內容欄 | `update_segment` / `update_scene` | 寫完 segment 後呼叫 `sync_segment_to_draft` |
| 在 PreprocessingView 存草稿 | `save_draft`（`files.py`） | 存完草稿後呼叫 `sync_draft_to_segments` |
| 在 SourceTextPanel 改段落 | （新增，見 3.4） | 走 `save_draft` 同一路徑 |

> 擴散在後端 handler 內完成，前端三處各打既有 API 即可，不在前端拼接/拆分。

### 3.3 提示詞佈局（`PromptColumn`）

Image / Video Prompt 兩塊由「標題列右側塞控制項」改為三段式垂直結構：

```
┌─ Video Prompt ────────┐   ← 標題列只留圖示 + 標題
│ [描述輸入框 textarea]   │   ← 中間：AutoTextarea / 結構化 editor
├───────────────────────┤
│ [選模型 ▾]   [✨ AI 產生] │   ← 下方一整列：下拉(寬) + 按鈕
└───────────────────────┘
```

- 移除標題列右側的 `ProviderModelSelect` + 按鈕。
- 新增底部一列：`ProviderModelSelect` 寬度放大（不再 `w-32`，改 flex 佔位），按鈕字級從 `text-[10px]` 提升。
- Image 與 Video 兩塊共用同一個小元件（如 `PromptModelToolbar`），避免兩處重複 JSX。
- 沿用既有 `textModel` state 與 `handleGenerateImagePromptAI` / `handleGenerateVideoPromptAI`，**不改生成邏輯**（已確認無功能性 bug）。

### 3.4 drama 第一欄可編輯（`TextColumn`）

`TextColumn` 目前 narration 分支有可編輯原文框，drama 分支只渲染唯讀對話列。改為：

- drama 分支在對話列下方（或上方）加一個可編輯的「場景描述」textarea，綁定 `scene_description`，走與 narration 原文框相同的 `onUpdateSourceText` 流程。
- narration / drama 共用同一個「原文編輯框」子元件，差異只有標題（「原文」/「場景描述」）與目標欄位。對話列維持唯讀顯示。

## 4. 資料流

### 編 segment 內容欄
```
SegmentCard textarea blur
  → onUpdateSourceText (既有)
  → API.updateSegment / updateScene
  → 後端寫 script + sync_segment_to_draft 更新草稿列(重算字數)
  → refreshProject + invalidateSourceFiles
  → SourceTextPanel / PreprocessingView 重新拉到新草稿
```

### 編 Step 1 草稿
```
PreprocessingView / SourceTextPanel 儲存
  → API.saveDraft
  → 後端寫草稿 + sync_draft_to_segments 依 ID 回寫各 segment
  → refreshProject
  → SegmentCard 顯示新內容
```

---

## 5. 錯誤處理與邊界

- **ID 對不上**：草稿列 ID 在 script 找不到 → 略過該列、記 log，不中斷其餘同步。
- **草稿不存在**：segment → draft 同步時若草稿檔不存在，跳過擴散（不自動建檔），避免在未做預處理時生出半成品草稿。
- **drama 對話 vs 場景描述**：雙向同步只涉及 `scene_description`（表格第 2 欄），**不觸碰對話列**（對話存在 `video_prompt.dialogue`，屬另一層）。
- **欄位數不符**：草稿列 cell 數少於預期 → 用既有 parser 的容錯（`len(parts) >= 3` 才取），渲染時補齊缺欄。
- **無限迴圈防護**：segment→draft 與 draft→segment 都是「寫入目標 + 重算」的冪等操作，不互相再觸發 API（擴散在後端單向完成，前端 refresh 只讀不寫）。

## 6. 測試

### 後端（`lib/step1_draft_sync.py`）
- `parse_draft_table`：narration / drama 表格各解析出正確列數與內容；表頭、`---` 列被排除。
- `render_draft_table`：round-trip（parse → render → parse）內容欄一致；字數欄依內容重算。
- `sync_segment_to_draft`：改某 segment → 草稿對應列內容與字數更新，其餘列不動。
- `sync_draft_to_segments`：改草稿某列 → 對應 segment 內容欄更新；ID 對不上的列被略過。
- 兩模式以參數化測試共用同一批案例。

### 前端
- `PromptColumn`：佈局快照 / 渲染——模型下拉與 AI 產生按鈕出現在 textarea 下方；Image 與 Video 兩塊都套用。
- `TextColumn`（drama）：渲染出可編輯場景描述框，blur 觸發 `onUpdateSourceText`。
- `SourceTextPanel`：段落可編輯、儲存呼叫 saveDraft。

### 整合
- narration：SegmentCard 改原文 → 切到預處理 tab 看到草稿更新；反向亦然。
- drama：同上以場景描述驗證。
